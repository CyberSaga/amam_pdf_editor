## 1. Goal, scope, non-goals

**Goal.** In a new 「編輯向量物件」 mode the user clicks or drags a marquee over CAD line work, sees what is selected, presses Delete (M1) or drags it (M2), can undo, and the saved file reopens with exactly that change and nothing else.

**Acceptance standard.** Every path that was not selected keeps its bytes, its order and its pixels. Save and reopen give the same result.

**Non-goals (M1, M2).** Resize and rotate handles, colour and width editing, z-order commands, cut/copy/paste, grouping, paths inside Form XObjects, patterns or Type 3 glyphs, cross-page moves.

## 3. Object model (question 1)

- **D1. One object is one painted path.** A record covers the bytes from the first path-construction operand after the previous paint to the end of its paint operator (`S s f F f* B B* b b*`). This is what the vendor selects with one click and it exists in every stream shape. A `q..Q` block is not the unit (346 counter-examples, and cumulative-`cm` streams have no blocks).
- **D3. No automatic grouping.** No proximity clustering and no "symbol" detection: the result would be unpredictable and the vendor does not do it. A later explicit command 「選取相連物件」 (flood through shared endpoints) is an M3 candidate.
- **Click** selects the topmost editable path whose geometry lies within 3 screen pixels of the point (stroke: distance to its centreline, widened to half the line width when that is known from `w`; fill: point inside, or within tolerance of its outline). Shift+click adds or removes one. A click on nothing clears.
- **D2. Marquee selects by geometry, not by bbox.** Touch (default): a path is selected when one of its segments intersects the rectangle or lies inside it. Contain (Alt): its bbox lies inside. A fill counts through its outline only, so a marquee drawn inside a large filled background does not select the background. Shift adds to the selection.
- **D18. Geometry means the path as constructed, not the painted shape.** A stroke counts through its centreline: line width, caps and joins are ignored by the marquee, and a dashed stroke counts as continuous (its gaps select too). Lines and rectangles are tested exactly. A curve is tested through chords that stay within ε = 0.01 pt of it (proposed; §4.1), so a curve farther than ε from the rectangle is never selected and one that enters it by more than ε always is. P3 checks whether the vendor behaves the same.
- **Outlined text** behaves as in the vendor tool: each glyph outline is a path, so a marquee over half a label removes half of it.
- **Huge selections stay usable** because a selection is a mask, not a list (§7.2). There is no cap on selection size. Caps apply to the page: decoded stream over 256 MiB or more than 4 M paints refuses the page (S0 tunes both).
- **Progress and cancel.** Index build and edit planning run in a worker with a cancel flag. Cancel before the commit step costs nothing because the document has not been touched.

## 4. Index (question 2)

### 4.1 Tables

All numpy, no MuPDF objects, so nothing in the index can outlive a mutation window (PITFALLS "A PageInterpretation must not outlive…").

| Table | Columns |
|---|---|
| paths (N rows, stream order = z-order) | `path_start`, `paint_end` (int64 offsets into the concatenated decoded streams), `block` (int32, −1 if none), `paint` (uint8), `flags` (uint16), `bbox` (float32 × 4), `line_width` (float32, page units), `ctm` (float64 × 6), `seg_start`, `seg_count` (int32) |
| cubics (C rows, exact) | 8 × float64 control coordinates in unrotated page space, `path` (int32), `seg_start`, `seg_count`. `v` and `y` are stored as full cubics. Only curves get exact rows (5,596 `c` on the sample, under 1 MB): a line's float64 row in `segments` is already exact. |
| segments (K rows, for queries, the overlay, and O-scan's lines) | `x0 y0 x1 y1` (**float64**, unrotated page space; float32 has a spacing of about 0.001 pt at 14,400 pt and worse beyond, which would eat the 1e-3 pt and ε budgets, Codex G4; cost about +18 MB on the sample, an estimate; the array handed to the view may be float32, it is display only), `path` (int32), `from_cubic` (bool). A line is stored once, here; `re` gives 4 lines. A cubic is flattened **after** its CTM is applied, into `n = ceil(sqrt(0.75 · M / ε))` equal-parameter chords, where `M` is the larger of `|P0 − 2·P1 + P2|` and `|P1 − 2·P2 + P3|` and ε = 0.01 pt (proposed). The bound is Wang's formula for degree 3, a proved worst case for equal-parameter subdivision, so it holds for every curve; float64 storage adds rounding far below ε (under 1e-9 pt at page scale). The `bbox` column stays float32 but is widened outward by one float32 step, so it can only over-include. Step 4's sampling test checks the implementation of the formula, it is not the proof. `n` has no cap; a page whose chords would exceed 8 M rows (proposed) is refused, never flattened more coarsely. |
| blocks (leaf `q..Q` pairs) | `q_start`, `q_end` (int64), `n_paints`, `inert` (bool), `n_cm`, `cm_operand_start`, `cm_operand_end` |
| streams | `xref`, `global_start`, `length`, `raw_key` (BLAKE2b of the stored bytes) |

Estimated size for the sample: about 80 MB (41 MB paths, 22 MB segments, 16 MB blocks; the cubics table and the chords of 5,596 curves add little, an estimate). S0-P1 measures it.

**D15. The index is a function of the decoded bytes and the page frame, and of nothing else.** The scanner's signature takes the ordered decoded streams and six frame numbers; it never sees the document, so it cannot read `/Resources`. Two columns were audited against this:

- `line_width` comes from `w` and the CTM only. Once a `gs` runs in the current state, the width is unknown (NaN) until the next `w` or the restoring `Q`, because `/ExtGState` may set `/LW`. The width only widens the click tolerance; no edit decision reads it.
- `IN_OC` is set from the `/OC … BDC` operator in the bytes. M1 does not look the property up, so every `/OC` section is non-editable whatever the resources say.

Step 3 pins this with a test that passes the scanner bytes only.

**Cache.** LRU with a 256 MB byte budget. The key is the ordered per-stream decoded SHA-256 plus the six frame numbers. A fast alias avoids the decode: per stream, BLAKE2b of the stored bytes **and** a sorted-key digest of the stream dictionary (as `_canonical_object_digest`, `model/text_commit/inspect.py`). The alias is used only when the dictionary's text holds no indirect reference at all: that digest records a reference, not the object behind it, so an indirect `/Filter` or `/DecodeParms` could change the decoded bytes under an unchanged alias (Codex G1). With any reference present the lookup decodes and uses the SHA-256 (about 75 ms). The stored bytes alone are not a key: the same bytes under a different `/Filter` or `/DecodeParms` decode differently (PITFALLS "A snapshot comparison that reads only decoded stream bytes…"). No xref is in either key, because a secure save renumbers the live document; the `xref` column is re-bound from the live page at lookup.

**Flags:** `EDITABLE`, `DEGENERATE` (no segment), `SETS_CLIP`, `CLIPPED`, `IMPURE`, `SPANS_STREAMS`, `IN_OC`, `CTM_SINGULAR`, `PAGE_ANCHORED` (D21). Page-level: `indexed_end`, the offset where indexing stopped (the stream end, or the first `BI` whose end is not proved; D14).

**Space.** Geometry is stored in unrotated page space: user space through `page_user_space_matrix(page)` (`model/pdf_content_ops.py`, the `PageVisualFrame` chokepoint). The view speaks visual coordinates; the model converts with the existing helpers in `model/geometry.py`, as native images do. A visual marquee stays axis-aligned under quarter turns. Step 3 pins the mapping on `/Rotate` 90/180/270, an offset CropBox and `/UserUnit 2`.

### 4.2 Scanner

- **D5. One general scanner (G) is the reference; F (below) is what ships for large pages (revision 10).** G decides every refusal and is the oracle F must equal; S0 measured about 5 s for G's token pass alone on the sample, so G alone fails B1. G: a single compiled alternation claims strings, hex strings, dictionaries, comments, array brackets, names and plain words at C level; a Python loop keeps the `q/Q` stack and the CTM (Python floats, `affine_concat`) and appends rows to growable buffers. Text objects are **lexed, not skipped** (revision 10; revision 2 skipped them whole): state set inside `BT … ET` outlives `ET` (`gs`, colour, `w`), and a text render mode 4 to 7 adds the text to the clip at `ET`, so from that `ET` to the restoring `Q` paths are `CLIPPED`. Text-showing and positioning operators contribute no geometry. Cost on the sample: 4 to 6 s is an estimate from the simplified probe (about 4 s for 37 MB, without vertices or a full CTM); P1 measures the real scanner.
- **D14 (revision 10, unreviewed). The scanner stops at the first inline image whose end is not proved.** After a `BI` and its dictionary, `inline_image_end(buf, pos)` returns a proved payload end or nothing. The proof reads bytes only (D15):
  1. `/L` (or `/Length`) states the length.
  2. No filter, and `/IM true` or a device colour space (`/G`, `/RGB`, `/CMYK`, or an Indexed array): length = height × ceil(width × components × bits / 8).
  3. Otherwise the **outermost** filter decides, because the stored bytes are in its format: `A85` ends at the first `~>` (`~` is not an ASCII85 data character, so the chains A85+Fl and A85+LZW need no second step); `AHx` at the first `>`; `Fl` where zlib reports its end; `DCT` at EOI by a marker walk; `RL` at its EOD byte.
  4. After the proved end: optional whitespace, then `EI`, then whitespace or a delimiter. Anything else is unproved.

  Unproved, so the scan stops there as before: an unfiltered image with a named colour space (its component count is in `/Resources`, which the scanner never reads), `LZW`, `CCF`, `JBIG2`, `JPX`, a malformed dictionary, a proved end with no `EI`. The function is the shared one of `plans/inline-image-boundary.md` (one implementation for both lexers); until it exists every image is unproved and the stop rule below applies unchanged, so M1 does not depend on it. **Measured (P11, 4,451 files, 27,768 pages of `test_files/`):** 246 pages (0.9%) hold a real `BI` (outside strings and comments). **By page, 218 of the 246 (89%) are proved in full.** By image the picture is the reverse, because two pages of two files hold 151,963 `CCF` images (text drawn as fax bitmaps): of 174,629 images, 20,054 (11.5%) are proved with `EI` in place (16,676 computed, 3,311 `Fl`, 37 `A85`, 26 `DCT`, 4 `AHx`), 151,977 are `CCF`, 1,689 unfiltered with a named colour space (two pages of one file), 887 `Fl` that zlib rejects, 9 `LZW`, 10 malformed (`/L` was stated on 2 images and wrong on both). Paint operators after the first `BI`: 133,602 on 75 pages, of which 122,488 on one `CCF` page; 10,504 are on fully proved pages. None of the CAD candidates holds a `BI`. The product's first-`EI` rule (`_scan_inline_image_payload`, run on those files) ends 4 ASCII85 payloads in 3 files too early, at a line break followed by `EI(` or `EI[` inside the data: that is the reason not to call it. *The stop rule (revision 2), now the fallback:* lexing is exact up to the first `BI` operator word outside a string or comment. Where the payload after `ID` ends cannot be proved: `pdf_lexer._scan_inline_image_payload` takes the first whitespace-delimited `EI`, which binary payload can contain. So the scanner never calls it. It sets `indexed_end` to the offset of that `BI` and indexes nothing after it. Edits before `indexed_end` are still exact: a splice only removes proved spans and copies every later byte verbatim, and a path span or an inert block changes no state that later content sees. The status bar says 「此頁含內嵌影像，其後的向量物件無法選取」. The proof is built after M1 (O9, decided), so in M1 every inline image stops the scan. The same heuristic serves the text-commit engine; that is outside this plan and logged in §14 (R9).

P1 measures G and chunked F side by side; G stays the reference and the fallback for streams F does not admit. The unchunked prototype peaked at 1.25 GB against the 400 MB gate, so chunking is part of the measurement, not an option. If chunked F also fails B1, the next step is a scan of the displayed page started at idle before the mode is entered (cancellable; needs F, because G would hold the GIL while the user scrolls); if that fails too, the owner decides. numpy tokenisation in 4 MB chunks cut at whitespace. (Revision 2 admitted a stream by a byte-class test and sent the rest to G; superseded by the mask stage in the next bullet.) Contract: F and G return equal tables on every fixture, on fuzzed streams and on the sample, plus a linear-time guard (PITFALLS "A byte-by-byte Python lexer…").
- **F after S0 (revision 10, unreviewed; probes P1, P12 to P14).** Four stages:
  1. *Mask.* One C-level search hops between `(`, `<`, `%` and the word `BI`. Each string, hex string, dictionary, comment and proved inline image (D14) is blanked in a tokenising copy; offsets do not change. Text objects are not blanked, only their strings, so the operators inside them are tokenised like any other (see G above for why). Python runs once per span, not per token. The probe (P14) blanked whole `BT … ET` objects, 918 spans on the stress page; blanking per string gives more spans and is not measured. **Why not "admit or G":** the byte-class admission passes 3 of the 122 path-heavy pages (5,000 paints or more) of the CAD candidates; the other 119 hold `<` and `BT` (P12), so nearly every real drawing would have gone to G. An unterminated span sends the page to G, which refuses it.
  2. *Tokenise* the copy in chunks cut at whitespace, on a thread pool. Three token classes: number, operator, and **name** (a token whose preceding byte is `/`); without the name class `/S` would read as a paint operator. `[` and `]` are blanked.
  3. *CTM by level.* Scopes of one `q` depth never interleave, so they are contiguous runs. For each depth in turn, the `cm`s of every scope are applied in stream order, vectorised across scopes by their rank inside the scope; a level whose longest run exceeds 64 `cm`s (the cumulative-`cm` shape) takes a plain loop over that level's `cm`s only. The arithmetic and its order are G's, so the result is **bit-equal** to G's loop (P13: the sample, the vendor file and the stress page) and the F = G contract stays plain equality. `Q` below depth 0 goes to G.
  4. *Geometry* (primitives, chords, boxes), built in batches of paths so the temporaries stay bounded.

  The state behind the flags. **Revision 11 (review M7): they do not all have one shape.** Clip active, `gs` seen, non-device colour space and line width are "the last setter in my scope chain" and are computed in stage 3's level pass. Two are not. *The open-path bit* outlives `q` and `Q` (`q 0 0 m 9 9 l S 5 5 m 6 6 l Q S`): it is a forward fill over construction and paint events in stream order, with no reference to depth. *`/OC` depth* follows `BDC`/`BMC` … `EMC`, which nest independently of `q`/`Q`: marked-content depth is a running sum, each `/OC BDC` is paired with the first `EMC` that returns to its depth, and `IN_OC` is the running sum of those intervals. Getting this wrong would make a path on a hidden layer selectable and deletable, so Step 3 has fixtures with `BDC` opened inside a `q` and closed after its `Q`, and the reverse. **None of the flags is prototyped**; Step 3 measures them.
  **Revision 11, three smaller rules (review m1, m2, m4).** *Numbers:* F's vector parse is used only for a token of digits, one optional sign and one optional point with at most 15 significant digits; any other number token goes through Python `float()`, the call G uses, so the two agree by construction and reject the same malformed tokens. *Words:* `BI`, `BT`, `ET`, `ID`, `EI` count as operators only when the preceding byte is whitespace or a delimiter other than `/`; a dictionary ends at its matching `>>`, with `<41>` inside it read as a hex string. *Memory and time:* stage 3's arrays are built per batch of structural operators as well (P13 held 302 MB of matrices at 6.3 M operators); O10's budget is stated per decoded MB and per structural operator, because the two pages measured differ (0.075 against 0.128 s per MB).

  **Numbers (this machine, offline, wall time only).** Sample: 2.3 to 2.5 s at 4 workers, 2.6 s at 2 (mask 0.7 s, tokenise 1.0 s, CTM 0.25 s, geometry 0.45 s). The mask's 0.7 s on a stream with no span is the cost of the probe's regex and the copy; a `bytes.find` hop should cut it (not measured). Stress page (`hvac-dwg.pdf` page 29, 72.8 MB, 1.10 M paints, 6.3 M `q`/`Q`/`cm`, depth 3): 9.3 s at 4 workers (mask 1.7, tokenise 3.2, CTM 2.7, geometry 1.6), 11.6 s at 1; the level CTM alone is 2.0 s against the loop's 6.2 s. **Memory:** the sample peaks about 600 MB above baseline (280 MB after tokenising in 250 kB chunks; the unbatched geometry stage is the peak), the stress page about 1.7 GB: the 400 MB bound is missed on both until stage 4 is batched. **Not measured:** GUI stall and panning while the scan runs in a QThread, the cost of the state flags, a 4-core machine.

  **Where the threads live.** The pool is a `concurrent.futures.ThreadPoolExecutor` inside `model/vector_paths/scan.py`, called from the coordinator's QThread worker and joined before it returns; it touches no Qt object and no document. The CI grep (`threading.Thread` in `view/` and `controller/`) does not reach it, but the written rule is "QThread + Signals only", so this is the owner's ruling (O11). The alternative that needs no ruling: the coordinator starts N QThread workers, one per chunk range, and merges.
- **Not used:** `tokenize_content_stream` / `parse_operators` (17.7 s, 2 GB) and `lex_content_stream` (byte-by-byte; its fast path hides exactly the path runs needed here). `lex_content_stream` is the slow, exact oracle in tests only.

### 4.3 Validity

- **Mutation gate (hard), read from the live document at commit.** A plan carries no xref. The commit takes `page.get_contents()` afresh and checks, in this order: (1) the stream count equals the plan's and each stream's decoded SHA-256 equals the plan's per-stream source digest; (2) the page frame equals the plan's six numbers; (3) the page's own `/Contents` lists no xref twice (the concatenated offsets would be ambiguous), and the page object appears once in the page tree (a loop over `doc.page_xref(i)`; the commit writes the page dictionary when it repoints `/Contents`, Opus M2; whether MuPDF loads a doubly listed page as two pages is a P4 fact); (4) the document is not encrypted, until P4 shows the write is safe there. Any failure refuses with `VECTOR_SELECTION_STALE` (1, 2) or `VECTOR_PAGE_UNSUPPORTED` (3, 4) and changes nothing (the F15-1 class: a selection older than the page). **D20. A shared stream is copied, never written (Codex G2).** A content stream can also be referenced by another page, as a Form XObject, as a tiling pattern, or by anything else; listing the kinds is the wrong shape of check. When the stream is not proved exclusive, the commit makes a new stream object with the new bytes and points this page's `/Contents` entry at it (a `/Contents` array that is itself an indirect object is replaced on the page by a direct array, so a shared array is not touched either). Every other referent keeps the old object and sees no change. **Whether a stream is exclusive is decided at the time of use, from the bytes, not remembered (Opus Q3, M3).** Revisions 3 to 7 kept a per-session set of created xrefs, guarded by a generation counter and an audit of every serialisation site; three review rounds found holes in that bookkeeping, and it rested on an unenforced invariant (no other feature ever adds a second reference to a live stream). **D20b, the primary design:** the commit already holds the transaction snapshot (`garbage=0` bytes of the whole document). It counts the occurrences of references in those bytes. **Exclusivity is a chain, not a per-object fact (Opus N1):** a stream is written in place only when every link holds: the page object is unique in the page tree (gate 3); the `/Contents` array, if it is an indirect object, is referenced exactly once; the stream is referenced exactly once. If any link fails, the edited streams are copied and the page gets a direct array. (Counting per object was wrong: two pages sharing an indirect array `[5 0 R]` leave stream 5 with a count of 1.) **The counting rule is fail-closed (Opus N2):** a reference to object N is the bytes `N`, whitespace, digits (any generation), whitespace, `R`, where the byte before `N` is not a digit and the byte after `R` is not a regular character; a count of 0 copies (it never refuses, the gate has already run); a snapshot containing `/ObjStm` copies everything. Every imprecision can only raise a count, which costs a copy and is safe: a match inside string or stream data, a leftover orphan that still names the stream. Nothing is stored between commits, so undo, redo, saves, renumbering, merges and other features need no hook. Cost: one C-level search over the snapshot (2 MB on the sample; an estimate of milliseconds). **What it needs from the library (P4):** in the `garbage=0` snapshot every live reference appears as plain `N G R` text outside compressed data (no object streams; `model/doc_bytes.py` sets `do_use_objstms=0` for the in-memory sink, the file sink is unverified), and the snapshot's numbering equals the live document's. **D20a, the fallback if P4 refutes that:** the created-xref set with a generation bumped in the `doc` setter and in `_bump_xref_epoch`, every `_note_live_doc_serialized` call moved before its library call, and one audit rule (every live serialisation at `garbage >= 2` is preceded by that note). `_save_doc` is a static method and cannot see the session, so the bump cannot live there (Opus M4); the new counter is not folded into `xref_epoch`, which is reinstated after handle swaps.

  **After S0 and the Opus findings (revision 10, unreviewed).** P4 measured the premises: the `garbage=0` snapshot has no `/ObjStm` and prints plain `N G R` with the live numbering for a plain source, an object-stream source and an AES-256 document (in-memory sink), so the `/ObjStm` rule is a guard that is not expected to fire (Opus P7); a page object listed twice in `/Kids` loads as two pages with the same xref, so gate 3's loop over `doc.page_xref(i)` sees it (Opus P5). **One link is added to the chain (Opus P6):** the stream dictionary's own outgoing values. If the text of the stream dictionary holds any indirect reference (`/Length 9 0 R`, an indirect `/Filter` or `/DecodeParms`), the stream is copied, and the copy's dictionary is written with direct values only: `/Length` by the library, `/Filter /FlateDecode`, no `/DecodeParms`, no `/DL`, every other key as it was. So the commit never writes through a reference that another stream may share. Whether `update_stream` writes `/Length` into the dictionary or into the referenced object is library behaviour: probe P16, pinned as a test. The encrypted-document refusal stays until the file sink and save and reopen are measured.

  Cost of a copy: the old stream stays for its other referents, so nothing is orphaned in the shared case; in the common unshared case there is no copy at all. P4 measures the mechanics (new object, `/Contents` repoint, effect on `xref_epoch` and on snapshot size). "Always copy" was rejected: one orphan per commit rides every snapshot and the undo stack reaches its 512 MiB budget after about 15 edits on the sample (Opus's estimate). This removes the "stream shared with another page" refusal. Resources need no check, because nothing in the plan depends on them (D15).
- **Query check (cheap).** The coordinator remembers the `(session_id, render_revision)` its index was valid for. When the revision moves it re-hashes the stored bytes (5 ms) and looks the key up in the LRU. On a miss it decodes and tries the SHA-256 (about 75 ms) before it rescans. Undo therefore finds the previous index again without a rescan, provided a snapshot restore keeps the stored bytes (only decoded equality was measured; P4 checks it).
- **After our own edit** the worker derives the new tables from the old ones (drop rows, shift offsets by the removed lengths). Contract: derived tables equal a fresh scan of the new stream, on every fixture. At commit, 64 random surviving rows are compared byte-for-byte between old and new stream; a mismatch drops the index and rescans.

### 4.4 Generality: what is edited, what is refused

Streams that are not isolated blocks are first-class, because nothing in §5 depends on blocks: cumulative `cm` (the vendor's output shape), shared state, nested `q`, several paints per block, multi-stream `/Contents`.

| Case | Rule |
|---|---|
| No provable page frame (`page_user_space_matrix` is `None`) | Page refused |
| Over the size caps | Page refused |
| Content stream or indirect `/Contents` array also referenced elsewhere (page, form, pattern) | Edited through a copy when not exclusive at the time of use (D20); the other referents are untouched |
| Page `/Contents` lists one xref twice, or the page object is listed twice in the page tree | Page refused |
| A `gs` or a non-device colour space in the path's state (`PAGE_ANCHORED`) | Delete allowed, move refused (D21) |
| Scan error before `indexed_end`: `Q` below depth 0, malformed number, unterminated string | Page refused |
| Inline image (`BI`) | End proved: skipped, indexing continues. End not proved: indexed up to that `BI`, nothing after it (D14) |
| Stream dictionary holds an indirect reference | Edited through a copy with direct values (§4.3) |
| Flattened chords over the row cap | Page refused |
| Encrypted document | Page refused. P4: the in-memory path works on AES-256; the file sink and save and reopen are not measured |
| Document fails the eligibility test at mode entry (D23 rule B: a no-edit save and reopen changes an object, capturing changes the live table, or one digest pass is over 400 ms) | Document refused for vector editing (O14); about 1.5% of `test_files/` |
| Path span holds a non-path operator (`IMPURE`), including `q` or `Q` between construction and paint | Record not editable |
| Path carries `W` or `W*` (`SETS_CLIP`), or paints with `n` | Record not editable |
| Span crosses a stream boundary | Record not editable |
| Inside `/OC` marked content (visibility unresolved in M1) | Record not editable |
| Singular CTM | Record not editable |
| A clip narrower than the page box is active (`CLIPPED`) | Delete allowed, move refused |
| Inside a Form XObject, pattern or Type 3 glyph | Not indexed (M3 for single-use depth-1 forms) |

Non-editable records never enter a selection; the handle reports how many were skipped. Every page refusal is one zh-TW sentence in the status bar and a code in the log. Nothing is guessed.

## 5. Edit semantics (question 3)

### 5.1 Delete

- **D7. Cut bytes, never re-serialise.** For each selected record remove `[path_start, paint_end)`. Keep the whitespace byte before it; drop the one after it only when both neighbours are whitespace. Tokens can therefore never join.
- **D17. Whole block only when provably neutral.** Remove `[q_start, q_end)` instead of the single spans when all four hold for a leaf `q..Q` block:
  1. **Allowlist.** Every token inside is a number, a name, or one of: `cm w J j M d ri i gs`, the colour operators (`g G rg RG k K cs CS sc SC scn SCN`), the construction operators (`m l c v y h re`) and the paint operators of D1. Anything else makes the block not inert: nested `q`, `Do`, `sh`, `n`, `W`, `W*`, text, inline image, marked content, `BX`, an unknown word. It is a list of what is allowed, not of what is forbidden.
  2. **No open path at either end.** The scanner tracks one bit, "a path is under construction". It is false at the `q` and false at the `Q`.
  3. **The block is exactly its records.** Every construction operator inside belongs to a record that starts and ends inside the block, and the number of such records equals the block's paint count (at least 1).
  4. **All of those records are editable and selected.**

  Rule 2 and 3 close the hole a plain "every paint selected" rule has: in `q 0 0 m 9 9 l S 5 5 m 6 6 l Q S` the one paint inside is selected, yet the block also holds construction that the `S` after `Q` may paint; in `0 0 m 9 9 l q 1 0 0 1 5 5 cm S Q` the path began outside. Both leave a path open at a boundary, so neither block is removed. In the first the inner record is pure and is deleted as a span; the record that crosses `Q` is `IMPURE`, as is the one in the second. On the sample this removes whole blocks, as the vendor does.
- **Why it is state-safe.** A path span holds only construction and paint operators, which change no graphics state. A block that passes D17 contains state operators, whose effect its own `Q` undoes, and complete selected paths; the current path is empty where it starts and where it ends. Removing it therefore removes those paints and nothing a survivor can observe. No `cm`, colour, `gs` or `q/Q` outside such a block is ever removed (PITFALLS "graphics state scoping requires tracking q/Q pairs"). What MuPDF itself does with a path left open across `q` or `Q` is measured in P2; the design does not depend on the answer, because those records are never edited.
- **Cumulative-`cm` streams.** The `cm` of a deleted record stays; later paths keep their place. Leftover `cm` runs are not compacted (that would re-serialise floats).
- **Z-order** of survivors is unchanged: their bytes and order are untouched.
- Adjacent ranges are merged before the splice, so the 308k-record run is one range.

### 5.2 Move (M2)

- The visual delta becomes a user-space delta `Δ` through the page frame's linear part. For a path with CTM `C`, the translation in its own space is `t = Δ · C_lin⁻¹`.
- **D8a. Rewrite the block's own `cm`** when the path's leaf block passes all four rules of D17 (the same proof: nothing but its own selected paths sees that `cm`), has exactly one `cm`, and that `cm` precedes its first construction operator: only operands `e f` change (`e += δx`, `f += δy` with `δ = Δ · C_outer_lin⁻¹`), written with `format_cm_value`.
- **D8b. Otherwise wrap:** replace the path span with `q 1 0 0 1 tx ty cm ` + the original bytes + ` Q`. This is valid in any shape, including cumulative `cm`. The wrapper is itself a block that D8a accepts, so a second move does not nest.
- Z-order unchanged. A pure translation does not change stroking. `CLIPPED` records refuse (they would slide under the old clip).
- **D21. A move refuses what is anchored to the page (Opus M5).** A tiling pattern and an ExtGState soft mask stay fixed in page space while the path moves, and the scanner cannot see resources (D15). So a move refuses any path whose effective state holds a `gs`, or a colour space set by `cs`/`CS`/`scn`/`SCN` other than the device names; the flag `PAGE_ANCHORED` is set from the bytes. This over-refuses (a `gs` that only sets line width is refused too); P9 counts how often. Delete is unaffected. The builder defines "moved" as the appearance translated and its twins include a soft mask and a pattern, so O-rebuild forces this refusal instead of trusting it.

### 5.3 Write protocol

1. GUI thread: decode the page streams (0.05 s) and hand bytes, digest and index to the worker.
2. Worker (bytes only, never the `fitz.Document`): build the ranges, splice, `zlib.compress(level 6)`, derive the new tables. Cancel is checked between phases.
3. GUI thread, `PDFModel.commit_vector_plan`, one guarded step:
   - **Gate** (§4.3). Nothing is written before it passes.
   - **Capture.** The transaction snapshot (also the command's before-state), `vector_page_prestate`, and copies of `pending_edits`, `edit_count`, `secure_save_required`.
   - **Target (D20).** A stream proved exclusive at this moment is written in place. Any other stream is copied: a new object gets the old dictionary, the page's `/Contents` entry is pointed at it, and the write below goes to the new object. A failure takes the single failure path below.
   - **Write.** `update_stream(xref, z, compress=False)`, then set the dictionary: `/Filter` becomes the single name `/FlateDecode` (a filter array is replaced, not extended); `/DecodeParms` and `/DL` are removed; every other key keeps its value.
   - **Post-check.** The stream decodes to the planned digest, and the dictionary equals the captured one except for `/Length`, `/Filter`, `/DecodeParms`, `/DL` (compared ignoring key order only).
   - **Failure: one path, whatever failed (Codex H3).** The page dictionary, the streams and the bookkeeping are one transaction. On any exception or failed post-check after the first mutating call: `_restore_doc_after_failed_mutation(snapshot)`, the three bookkeeping values put back (the `_restore_delete_transaction` precedent, `model/pdf_object_ops.py`), every page's text index dropped, a refusal recorded. No partial repair is attempted (`restore_stream_storage` and "put `/Contents` back" are not used): a repair can itself fail half-way, and the snapshot restore costs 1 ms here. Then the pre-state is **verified**, not assumed, by one function, `vector_page_prestate(doc, page)`: the page's `/Contents` value, each stream's decoded digest, and each stream dictionary in a **normal form**: key order ignored, `/Length` left out (it is derived), and an indirect reference to a scalar replaced by the scalar. The normal form exists because a snapshot restore reopens bytes from a non-incremental save, which the repository records as turning an indirect `/Length N 0 R` into a direct integer (`model/text_commit/inspect.py`, `StreamStorage` docstring); a plain dictionary comparison would report a correct rollback as damage on such files (Opus M1). The rule is not trusted by inspection: the **null-transaction self-test** (§9, calibration) runs capture → restore with no mutation on every fixture shape and requires equality. It is captured before the first mutating call and compared after the restore; a difference latches the session damaged (today's helper latches only when the restore raises, so this comparison is new). O-dict and the fault matrix call the same function (Codex K2), so the runtime check and the tests cannot drift apart. A failure before the first mutating call restores nothing and does not swap the document handle; every check that can refuse (the gate) runs before Capture. **Scope of "changes nothing" after a rollback (Opus M8):** page content, dictionaries in normal form and bookkeeping. The handle swap itself has the side effects every existing rollback has (the next save is a full save; stored form normalised); they are not undone.
   - **Success.** `edit_count += 1`; latch `secure_save_required` for a delete; install the new index; invalidate what describes the page's content (D19).
4. Controller: `SnapshotCommand` (`vector_delete` / `vector_move`), `_invalidate_active_render_state()`, `show_page`, clear or rebase the selection, `_update_undo_redo_tooltips()`.

- **D9.** The default `update_stream` is not used: it compresses on the GUI thread (1.64 s per edit on the sample).
- **D11.** Vector edits do not call `mark_page_content_dirty`, so they queue no `clean_contents` pass (0.9 s, changes the digest, leaves 29.8 MB uncompressed, which would make every later snapshot about 30 MB). Checked: `pending_edits` is read only by the clean pass, the `MaintenanceBook`, page renumbering, the delete rollback and the session-transfer dirty flag (which also reads `edit_count`). Unsaved state comes from the command stack (`session_has_unsaved_changes`), so the recorded `SnapshotCommand` marks the document modified. The page's Tier-0 fidelity protection stays, which is right: no byte outside the cut ranges changes.
- **D16. A page already queued for `clean_contents` (two guarantee classes).** D11 stops this feature from queuing a page; it cannot stop a page from being queued already. `apply_pending_redactions()` at save cleans every queued page that is not fidelity-protected, whatever happened since. So:
  - **Class A** (the page has no queue entry, or is fidelity-protected, when it is saved): unselected bytes are preserved through save and reopen. O-bytes applies across the save. **Premise, conditional on P8:** a delete latches a secure save. Codex read that path (round 2, G5): garbage level 1, no `clean`, no `deflate` requested, which suggests the decoded bytes survive but does not prove it through both serialisation passes. P8 runs exactly this: class A delete, secure save, reopen, decoded-byte comparison. If the secure save rewrites streams, class A holds for moves only and deletes fall to class B at save.
  - **Class B** (every other page: it has a queue entry and is not fidelity-protected when it is saved, whether the entry came before or after the vector edit; the two classes are exclusive and cover all pages): the commit is still byte-exact in the session, but the save rewrites the stream. After save the guarantee is O-struct and O-pixel, not bytes. That page had already lost byte identity to the earlier edit.
  - The vector commit neither adds nor removes queue entries and never calls `_maybe_garbage_collect`. Its `edit_count += 1` can only change when another feature's own edit runs the interactive clean, which is scoped to that edit's page and undo unit.
  - A save is one of the events that drop the vector selection and the coordinator's "index valid" mark (§8); the gate of §4.3 catches whatever slips through.
  - Undo and redo across a save restore the command's snapshots and their `MaintenanceBook`, as for every other command.
  - Whether a save re-compresses the cleaned stream, and how large later snapshots of a class B page are, are library facts: P8.
- **D19. What a commit invalidates.** The existing object operations rebuild the page's text index eagerly after a stream rewrite (`block_manager.rebuild_page`, `model/pdf_object_ops.py`). A vector edit cannot change any text span (text operators make a span `IMPURE` and a block not inert), but an index that predates a content change must not be trusted on that argument alone. The commit therefore marks the page stale through a new `TextBlockManager.mark_page_stale(page_idx)` (today only page-shifting operations set that state), so `ensure_page_index_built` rebuilds it before the next search or text edit, and calls `invalidate(page_idx)` on `PDFModel._source_run_resolver` (`SourceRunResolver`, `model/text_commit/source_run.py`). It is lazy because the rebuild cost on a 414k-path page is unmeasured (P8). The controller does what `delete_object` does today (`controller/pdf_controller.py`): `_invalidate_active_render_state()`, record the command, `show_page`, refresh the tooltips; it invalidates nothing else. Nothing calls `mark_page_content_dirty`.
- **The vendor's own output** is handled like any other stream: its watermark group is a `Do` inside marked content (ignored), its paths are editable.

## 6. Undo and memory (question 4)

- **D10. Use the existing `SnapshotCommand`.** Measured on the sample: before-snapshot 23 ms and 2.1 MB, after-snapshot under 1 MB, restore 1 ms. It already carries the `MaintenanceBook`, page state and xref-epoch handling. A delta command would need its own stale gates and a second restore path for no measured gain.
- **Worst case.** A stream stored uncompressed (for example after another feature's `clean_contents`): the first before-snapshot is about 30 MB. Later ones are small again because our commit always writes Flate. That fits `MAX_UNDO_STACK_BYTES` (512 MiB).
- **The real undo cost is the index,** not the bytes. The LRU keeps the previous table, so undo and redo do not rescan (§4.3).
- **Memory budget.** Index cache 256 MB total. Selection mask N bytes (0.4 MB on the sample). Overlay segments at most 16 MB (1 M segments). Scan peak under 400 MB above baseline (gate B1).

## 9. Fidelity, oracles and tests (question 7)

**Fixtures.** The two owner files are never committed. Sample tests read them from the gitignored `test_files/cad_vector/` (`before.pdf`, `after_vendor.pdf`), carry `needs_fixtures` and skip themselves when absent. CI deselects that marker, so **every red-light test runs on synthetic twins** from `test_scripts/vector_fixture_builder.py`: isolated blocks, cumulative `cm`, nested `q`, several paints per block, a scaled and rotated `cm`, dash arrays, a text object whose string holds `(0 0 m 9 9 l S Q)`, a comment holding operators, an inline image whose payload holds ` S `, a clip, `/OC` content, a Form XObject, a two-stream `/Contents`, `/Rotate` 0/90/180/270, an offset CropBox, `/UserUnit 2`.

**Oracles** (none of them uses our scanner to judge our scanner). Each names its independent source, its domain and what it does not cover.

- **Domain (Codex G3).** MuPDF reports drawings the index does not hold: those inside Form XObjects and those after the first `BI`. The comparable set is built without the scanner: a temporary copy of the page whose content is cut at the first `BI` token found by the reference lexer (exact up to there), closed with the `Q`s needed to balance, and whose `/XObject` resources are emptied. `get_cdrawings` of that copy is the **comparable list**; O-scan runs against it. Everything else MuPDF draws on the real page is the **unindexed remainder**, covered by O-struct's full-page check.
- **O-rebuild (twins only; the total oracle, Codex G6, H1, H2).** The fixture builder writes each twin from a list of paths. For any edit it can also write the **expected document** directly: the same list without the deleted paths, or with the moved paths' coordinates shifted. The check is on the outcome, for delete and move alike, with no mapping and no per-case rule. **It compares the whole document, not the edited page (Opus N1):** a write that leaks into another referent of the stream is invisible to anything that looks at one page. So besides the edited page, every other page's `get_cdrawings` and render, and the decoded bytes of every Form XObject, pattern and annotation appearance stream, equal the expected document's. The generator randomises the reference topology around the edited stream: a second page sharing it, a shared indirect `/Contents` array, a form, a pattern or an `/AP` stream pointing at it, an orphan object naming it, and neighbouring object numbers that are substrings of each other (5 and 15).
  1. `get_cdrawings` of our edited page equals that of the expected document, item for item and in order.
  2. The two renders are equal pixel for pixel over the whole page, inside the selected boxes too. This observes every state a renderer can show (clip, blend, soft mask, overprint).
  3. Which path the gesture means is stated by the test from the builder's list, not from the index: a click means the last-written path within tolerance (topmost), a marquee means every path touching it. Two identical coincident paths are both taken by a marquee; a click takes the later one, and when nothing is drawn between them either removal gives the same expected document, so they need not be told apart.
  4. A weaker byte check keeps the edit local: the builder records, per path, its own byte range and the widest range a legal plan may remove for it (its enclosing block and adjoining whitespace when D17 allows the block, else the path and adjoining whitespace). Every plan range lies inside the union of those envelopes for the selected paths and covers each selected path's own range. Whole-block deletion and the whitespace rule both pass; removing anything of an unselected path fails.

- **O-scan.** For every drawing of the comparable list there is an index row whose **primitives** match item by item, in the same order: a line's two points (from `segments`), a curve's four control points (from `cubics`), a rectangle's corners, each within 1e-3 pt. Chords flagged `from_cubic` are never compared, so no flattening enters this oracle. How MuPDF normalises items (a closing line for `h`, a rotated `re` as a quad) is read in P2 and the comparison follows it. Rows without a drawing must all be `DEGENERATE`. **S0-P2:** a row is `DEGENERATE` when its path has no segment; on the sample these are 1,981 `m h` paths, of which MuPDF omits 1,977 and draws 4 as zero-height items (rule not found). So the converse is not required: a `DEGENERATE` row may have a zero-extent drawing. With that rule the two lists align row for row on the sample. MuPDF reports a curve's rectangle as its control-polygon box, so boxes are never compared for curves, only primitives. `get_cdrawings` coordinates are in the unrotated frame; O-scan maps through the page frame first (`/Rotate 270` on the sample).
- **O-flat.** For every cubic on the twins, 2,000 points sampled on the exact curve (de Casteljau, in the test) lie within ε of the chord polyline, and every chord vertex lies on the curve. Twins: a cusp, a loop, a near-straight curve, a 5,000 pt curve, and each under a scaling, rotating and shearing `cm`.
- **O-struct.** Take the row-to-drawing mapping that O-scan built before the edit. After a delete, `get_cdrawings` equals the old list minus the drawings whose rows were all selected: same order, same type, colour, width, dashes, caps and items. A drawing MuPDF merged from two paints (`fs`) with only one of them selected stays, as the surviving half's type. After a move the selected drawings are translated by the delta and nothing else differs. A second, mapping-free check runs on the **full** page (forms and post-`BI` content included), stated per operation (Codex H1). Both lists are first normalised on MuPDF's side only: a drawing that carries both a fill and a stroke is split into a fill record and a stroke record, so a half-selected merged drawing is one record removed and no type change. *Delete:* the new list is an order-preserving subsequence of the old one and the multiset difference equals the selected records. *Move:* (a) as multisets, new = old − selected + selected shifted by Δ; no membership test is involved, so a path moved onto an identical existing one, or away from a duplicate, is counted correctly (Codex J1). (b) Order: take the records whose value occurs once in the old list and whose image (itself, or itself shifted if selected) occurs once in the new list; their sequence is the same in both lists. Records with duplicates are left out of (b): the mutual order of identical records cannot be observed by any renderer, and their position relative to the rest is covered by O-pixel. **Limit, stated:** on real files this is not a total oracle; an expected ordered list would need to know which occurrence of a duplicated drawing was selected, which only the index knows. The total oracle is O-rebuild on twins, whose builder covers collisions and duplicate multiplicities in both directions. Identical records need no pairing in either operation. Covers: order, and each survivor's type, geometry, colour, width, dashes, caps. Does not cover: clip, blend mode, soft mask, overprint, which MuPDF does not report per drawing; those are observed by O-pixel outside the selected boxes and by O-rebuild everywhere on twins. On real files, state that only shows inside a selected box and is not reported per drawing is unobserved; D17 is the argument there.
- **O-pixel.** Render before and after at 2× with annotations off. Outside the **changed region** the pixels are byte-identical. The changed region is, for a delete, the selected drawings' rectangles; for a move, the union of those and the same rectangles shifted by Δ (Codex L1). The rectangles and their growth are defined once, in "Tolerances and sources" below: MuPDF's own rectangles, never the index.
- **Calibration: every equality rule is itself tested both ways (the class check for both recurring classes, Opus Q5).** Six review rounds kept finding a comparison rule that was wrong for one shape: an oracle rejecting a correct edit, an oracle blind to a wrong one, a rollback verifier reporting a correct restore as damage. Listing more shapes does not end that. So each rule, oracle or runtime verifier, must pass two tests before it is used to judge anything:
  1. **Must pass** on a no-op or a known-correct transformation. For `vector_page_prestate`: the null transaction (capture, snapshot restore, compare, with no mutation). For the real-file oracles: every edit that O-rebuild accepts on a twin must also be accepted by O-struct (both forms), O-pixel, O-bytes and O-dict.
  2. **Must fail** on seeded wrong edits (a mutant suite): a neighbour's bytes cut, a state operator dropped, two paths swapped, the wrong one of two coincident duplicates removed under an occluder, a moved path whose mask stayed behind, a block removed with an open path. O-rebuild must reject every mutant; each real-file oracle must reject the mutants in the coverage it claims in the matrix below, and the matrix is corrected where it does not. **Mutants are derived by rule from the plan's own decisions, not from a hand list (Opus Q3):** for each decision that chooses between two actions, the mutant takes the other one: always write in place (D20), skip the copy, remove the block when a D17 rule fails, shift a range by one token (D7), wrap where D8a applies and rewrite where it does not, move a `PAGE_ANCHORED` path (D21), skip the restore, replay the `/Filter` write after the restore, leave `/Contents` repointed, leave an extra dictionary key, restore the decoded bytes under another filter. The last five are the must-fail cases of `vector_page_prestate` (Opus N3): a verifier that always answers "equal" passes the null transaction and blinds the fault matrix.
  3. **Must pass on product-shaped output (Opus N4).** For a move the builder also emits the same edit in the product's own byte forms (the `q 1 0 0 1 tx ty cm … Q` wrapper and the rewritten `e f` operands with six decimals). Every oracle must accept those, so a rule that is exact where a correct move is not fails here, in Step 2, and not on a correct implementation in Step 10.
  
  **D23. Two implementation rules (Opus; adopted by the owner 2026-11-17). They replace the listed expectations above where the two disagree.**
  - **Rule A: the mutant × oracle matrix is computed, not listed. Revision 11 (review M8): computed from ground truth, not from the oracle.** The builder emits, for every twin and operation, the expected document and a list of *facts* (which paths exist, their geometry in page space, which bytes outside the edited ranges are untouched, which objects may change). Each oracle declares its *domain*: the facts it is responsible for (O-struct: path set and geometry within the tolerance; O-bytes: bytes outside the edit; O-pixel: pixels outside the changed region; rule B: objects). A cell is **must kill** when the mutant's output violates a fact inside that oracle's domain; whether it does is decided by the builder's own comparison of the mutant with the expected document, in exact arithmetic on the builder's side, never by running the oracle. The oracle is then run and must reject every must-kill cell and accept every must-pass input. A mutant is **equivalent** only when the builder finds no violated fact at all (wrapping where D8a applies, writing in place on an exclusive topology; Opus P1); a mutant that violates a fact in no oracle's domain is a **coverage gap** and fails the run, so a blind spot is reported and not excused. Must-pass inputs are a column per oracle, so O-bytes is given product-shaped moves and not builder-shaped ones (Opus P2). A run with an empty must-kill column for an oracle fails: that oracle judges nothing.
  - **One tolerance function and one matching algorithm (Opus P3, P4; revision 11, review m3).** Two coordinates match when they differ by at most `max(1e-3 pt, k · ulp_float32(|x|))`, `k = 8`, checked by the must-pass column in Step 2 and changed only with a recorded reason. Records are paired without greed and without a global min-cost solve (infeasible at 300k records): records are bucketed on a grid of the tolerance, candidate pairs form a bipartite graph, and each connected component gets a maximum matching (Hopcroft–Karp); the sets match when every component is perfectly matched. The product writes move operands with enough digits for the path's CTM: the digit count is chosen so that the error after the CTM is under 1e-4 pt, instead of a fixed six decimals.
  - **Rule B: an object-level permitted-write diff.** On every twin, after every commit and after every rollback and undo, every object of the document is compared with the input's. Allowed to differ: the edited page object, in `/Contents` only; the streams the builder's topology marks exclusive to that page; new objects that are referenced from the edited page only. Anything else fails. The same harness walks `/Kids` itself to count page objects, independent of gate 3.
  - **Rule B at run time (O12, owner 2026-11-17: it runs on the user's document too; rewritten in revision 11 after review M4 to M6, unreviewed).** `model/vector_paths/commit_state.py` keeps a digest table with three kinds of entry: for every xref, a 16-byte hash of the object text plus the raw stream bytes; for a page object, two hashes, one of `/Contents` and one of everything else; and one entry for the trailer's keys other than `/ID` and `/Size` (`xref_object(-1)`). File containers (`/Type /ObjStm`, `/Type /XRef`) are recorded as a class and `/Length` is left out of a stream's hashed text, because a save changes both without changing the document (P17). The table also records every reference to an xref at or above `xref_length` (a dangling reference), found in the same pass.
    - *Before a commit* the writer declares its write set: the edited page's `/Contents` entry (the rest of the page object is not in the set), the stream xrefs D20b's chain decided to write at this moment, and the new xrefs it will create. A commit is refused before any write if the table holds a dangling reference to a number the commit would create (review M5c).
    - *After the commit*, on the GUI thread inside the guarded step: one pass recomputes the table. Any difference outside the declared set, including the page object outside `/Contents` and the trailer → restore the snapshot, refuse the edit, log the xrefs, tell the user (「編輯已取消：文件的其他部分發生了預期外的變更」). Each new xref must have exactly one reference after the commit, from the edited page (D20b's reference count, run on the new numbers).
    - *After a rollback or an undo*: the table must equal the pre-commit table (same `xref_length`, same entries). A restore is a reopen of serialised bytes (`_restore_doc_from_snapshot`); the two normalisations above are what makes this comparable. One table is kept per document revision and reused: the eligibility test below guarantees that capturing a snapshot does not change it, so a commit costs one pass, not two. A mismatch cannot be repaired by another restore, so it latches the document as failed for vector editing and says so.
    - *Eligibility, once at mode entry (O14).* Three conditions, each an outcome measured on this document and not an estimate from its size: (1) capturing a snapshot through `serialize_document_bytes` leaves the live table unchanged; (2) the table of the reopened snapshot equals the live table; (3) one live pass takes at most 400 ms, so that a commit (snapshot, write, one pass) stays inside B3. **The owner allowed B3 to be relaxed (2026-11-17): the commit stall limit is 500 ms, was 300 ms.** The 36.5 MB stress file measured 161 to 215 ms per pass. Step 5 reports the stall on the real CAD sets; a further change is again the owner's. - **Tolerances and sources (Opus M6).** A move writes `q 1 0 0 1 tx ty cm` or new `e f` operands with six decimals (`format_cm_value`) where the builder writes shifted coordinates, so for a move O-rebuild **and both forms of O-struct** match drawings within 1e-3 pt (the multiset and unique-record rules pair records by that tolerance, not by value equality) and compare pixels with a stated tolerance inside the changed region (proposed: at most 32/255 per channel; P8 measures what a correct move produces) and exactly outside it. Deletes stay exact. The changed region comes from MuPDF's own drawing rectangles before the edit, grown by half the reported width times the miter limit plus 1 px, never from the index. - **O-bytes.** The plan's ranges are an input to this oracle, and it verifies them instead of trusting them. `lex_content_stream` (coalescing off) is the reference lexer; it shares no code with the scanner.
  1. *Bytes.* The old stream with the ranges cut out equals the new stream, byte for byte.
  2. *Alignment.* Each range starts and ends on a token boundary of the reference lex of the old stream.
  3. *Tokens.* The reference lex of the new stream, as a list of (kind, bytes), equals the reference lex of the old stream without the tokens inside the ranges. This proves that no two tokens joined, that nothing outside the ranges lexes differently, and that there is no `MALFORMED` token.
  4. *Classes.* D7 merges adjacent ranges, so a range is a **sequence** of units. Each unit is either a path span (numbers, construction operators, then one paint operator) or one balanced `q … Q` over the D17 allowlist. Whitespace is free.
  5. *Open path.* The oracle derives its own "path under construction" bit from the reference lex (set by a construction operator, cleared by a paint operator or `n`). It is false at the start and at the end of every unit of check 4, and at the `q` and `Q` of every removed block. This is the independent witness for D17 rule 2.
  6. *Move.* For D8a the two lexes differ in exactly two number tokens, the `e` and `f` operands of one `cm`. For D8b the new lex is the old one plus the inserted `q 1 0 0 1 tx ty cm` before and `Q` after each wrapped span.
  
  State neutrality is not asserted here: no independent interpreter exists to compute "the state at each survivor". It is proved by D17's rules and **observed** by O-struct, where MuPDF reports every survivor's geometry, colour, width and dashes. Limits, stated: the reference lexer uses the same `EI` heuristic, so past a `BI` it is not independent; there the check is byte identity from `indexed_end` to the end, which needs no lexer. On the sample the byte-by-byte lex of 31.7 MB is slow (measured in P8); if it exceeds 5 min the sample runs checks 2 to 5 on windows around 200 sampled ranges and check 1 in full.
- **O-dict.** O-bytes and O-struct read decoded bytes and say nothing about the stream dictionary (PITFALLS "A snapshot comparison that reads only decoded stream bytes…"). The dictionary is covered separately: after a commit it equals the old one except `/Length`, `/Filter`, `/DecodeParms`, `/DL`; after a failed commit and after undo, both of which are snapshot restores (§5.3), there is **one pre-state comparison**, `vector_page_prestate` (§5.3), the same one the runtime rollback check and the fault matrix use: the page's `/Contents` value, each stream's decoded digest, and each stream dictionary in the normal form of §5.3 (key order ignored, `/Length` left out, indirect scalars resolved; a restore may reorder keys and make an indirect `/Length` direct). Stored-byte identity is not asserted; P4 reports whether it holds.
- **O-reopen.** `save_as`, reopen, then O-struct and O-pixel against the pre-edit document. Where `PDF_EDITOR_PDFTOPPM` is set, Poppler's render of the saved file agrees with MuPDF's within tolerance (catches syntax MuPDF forgives).
- **O-vendor (sample only).** Derive the vendor's deleted set by order-free geometric matching (0.3 pt), delete exactly that set, and compare with the vendor file after masking its watermark groups and Link annotations: equal survivor multisets, and pixel differences under a tolerance set in S0-P3 (the vendor re-emits coordinates as float32). **S0-P3:** the derived set is 318,531 drawings (316,913 strokes 0.06 wide, 1,618 fills), one compact region, the same colours inside and outside it. The oracle deletes the derived set itself, so the region's ragged edge (about 0.2% of paths either way) does not enter it, and no marquee rectangle has to be recovered from the recording. Touch against contain is not a vendor-parity question: O1 decided it.

**Real-app check.** The `/verify` skill drives the app on the sample: enter the mode, marquee the bottom-right room, delete, undo, redo, save, reopen, with screenshots.

## 12. Decisions

- **D1.** Object = one painted path.
- **D2.** Geometric hit-testing; touch marquee by default, Alt for contain; fills count through their outline.
- **D3.** No automatic grouping.
- **D4.** Dedicated `vector` mode.
- **D5.** General scanner G is the reference and decides refusals; F ships in M1 (G fails B1, measured): mask, chunked tokenise with a name class, level-wise CTM bit-equal to G, batched geometry, under an equality contract. Fallbacks in order: idle pre-scan of the displayed page, owner decision.
- **D6.** No spatial index: the box-inside fast path meets B2 (11 to 14 ms, P15).
- **D7.** Delete cuts byte ranges; a whole block only when fully selected and inert; state operators are never removed.

## 13. Dead ends

- **Existing tokenizer as the index.** 17.7 s and 2 GB on the sample.
- **`get_cdrawings` as the index.** Exact geometry in 1.5 s but no byte offsets, and ordinal alignment is unprovable (the counts differ by 1,977). Kept as the test oracle.
- **`q..Q` block as the object.** 346 counter-examples in the sample; no blocks at all in cumulative-`cm` streams.
- **Bbox hit-testing.** A frame path's bbox covers the sheet; every marquee would select it.
- **Redaction to delete.** `apply_redactions` is geometric and destroys neighbours (the F13-VF-2b lesson).
- **Regenerating the stream from an object model** (what the vendor does). It rewrites every byte and moves coordinates by float32 rounding; this project's standard is that unselected content keeps its bytes.
- **Delta undo.** Not a failure, just unnecessary: the snapshot costs 23 ms and 2.1 MB.
- **Default `update_stream` on the GUI thread.** 1.64 s per edit.
- **`clean_contents` after an edit.** See D11.
- **Greedy in-order matching against the vendor file.** It stalled at record 79,144 of 95,076 and reported everything after that as removed. Its numbers are not used.

## 14. Risks

- **R1. Coverage beyond one sample.** CAD exports often wrap the page in a Form XObject, use clips, layers and real text. M1 may refuse much of such files. P9 measures it before M3 is ordered.
- **R2. GIL.** Scanner G in a QThread can make the GUI stutter. Gate B1; F (numpy releases the GIL) is expected in M1 for this reason too.
- **R3. Index and stream out of step.** Digest gate, derived-equals-rescan contract, sampled byte check at commit.
- **R4. Invisible content.** A marquee also selects paths hidden under images or drawn in white. The count is shown and undo exists; `/OC` content is excluded.
- **R5. Other features on the same page.** A textbox or legacy edit queues `clean_contents` for it: the stream changes shape, the index is rebuilt, snapshots grow to about 30 MB each. Not caused by this work; P8 measures it.
- **R6. Library behaviour.** D9 depends on PyMuPDF 1.27's `update_stream(compress=False)`; D20b on how a `garbage=0` write prints references (plain `N G R`, live numbering, no object streams). Both pinned by P4's tests; D20b is fail-closed where a premise breaks.
- **R7. Vendor parity tolerance.** Float32 re-emission and the trial watermark make exact comparison impossible; O-vendor is supplementary, O-struct and O-pixel are the standard.
- **R8. Incremental saves keep the old stream.** Hence O5.
- **R9. The `EI` heuristic outside this plan.** `pdf_lexer._scan_inline_image_payload` also bounds inline images for the text-commit engine. This plan avoids it (D14) but does not fix it.
